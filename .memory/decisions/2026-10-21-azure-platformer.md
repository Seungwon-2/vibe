# Decisions: Azure Platformer MVP

- Date: 2026-10-21
- Status: Confirmed

## D01. 첫 출시 범위
- **Chosen**: 사내에서 플레이 가능한 플랫포머 MVP. 싱글 플레이어 웹 게임으로 시작한다.
- **Rationale**: 사용자가 MVP 옵션을 선택했다. 로그인, 플레이, 이어하기, 랭킹과 월드 진행을 첫 범위에 포함한다.

## D02. Azure 배포 및 데이터 저장
- **Chosen**: Azure Static Web Apps에 React 웹앱을 배포하고, Azure Functions API와 Azure SQL을 사용한다.
- **Rationale**: 사내 표준이 없다고 확인했고, 추천 구성으로 진행하기로 했다. 저장 지점과 스테이지 최고 기록처럼 관계가 분명한 데이터를 SQL에 저장한다.

## D03. 게임 클라이언트 구조
- **Chosen**: React와 Phaser를 함께 사용한다. React는 로그인·메뉴·랭킹 UI를, Phaser는 게임 화면·물리·스테이지를 담당한다.
- **Rationale**: Phaser가 플랫포머의 충돌과 물리를 처리하고 React는 웹앱 화면을 관리하도록 역할을 나눈다.

## D04. 아트 방향과 캐릭터
- **Chosen**: 사용자가 제공한 참고 시트를 기준으로 생성한 도트 캐릭터를 첫 버전의 주인공으로 사용한다. 현재 주인공 이미지는 `assets/character/platformer-character-spritesheet-v2.png`와 `assets/character/platformer-character-actions-v1.png`다.
- **Rationale**: 사용자가 이 캐릭터를 주인공으로 개발하라고 명시했다. 도트 에셋은 이후 플레이어블 캐릭터 확장을 고려해 별도 리소스로 관리한다.

## D05. 월드와 스테이지 구성
- **Chosen**: 월드 2개, 각 4스테이지(총 8스테이지). 테마는 바람이 깃든 고대 유적과 지하 발광 광산이다. 각 월드의 4스테이지는 보스전이다.
- **Rationale**: 월드별 테마 차이와 보스전을 포함한 구성을 사용자가 선택했다.

## D06. 보스전
- **Chosen**: 보스마다 고유한 공격 패턴과 밟을 수 있는 순간을 둔다. 기본 처치 방식은 보스를 밟는 것이다.
- **Rationale**: 일반 적을 밟아 처치하는 핵심 동작을 유지하면서 보스별 공략 차이를 준다.

## D07. 조작 및 이동 속도 효과
- **Chosen**: 데스크톱 키보드 조작. 방향키 또는 WASD로 이동하고 Space로 점프, Shift로 달리기한다. 빨라지거나 느려지는 획득형 속도 아이템을 두며, 일부 스테이지 기믹도 이동 속도를 바꾼다. 속도 아이템 효과는 3초 지속하며, 새 아이템은 기존 효과를 교체하고 시간을 다시 시작한다.
- **Rationale**: 사용자는 데스크톱 키보드와 달리기를 선택했고, 아이템과 스테이지 기믹의 속도 효과 및 3초 지속·교체 동작을 지정했다.

## D08. 순차 해금
- **Chosen**: 이전 스테이지를 클리어해야 다음 스테이지가 열린다. 월드 보스를 이기면 다음 월드가 열린다.
- **Rationale**: 사용자가 순차 해금을 선택했다.

## D09. 라이프와 재시작
- **Chosen**: 월드 시작 시 라이프 5개를 지급하고, 해당 월드에서 공유한다. 라이프는 최대 9개다. 피격·함정으로 라이프를 잃으면 마지막 체크포인트에서 재시작하며 1.5초 무적이다. 라이프가 0이면 게임오버 후 현재 스테이지 처음부터 라이프 5개로 다시 시작한다. 다음 월드에 들어가면 라이프는 5개로 새로 시작한다.
- **Rationale**: 5개 공유, 최대 9개, 체크포인트 재시작, 게임오버 후 현재 스테이지 재시작과 5개 회복, 1.5초 무적을 사용자가 선택했다. 월드마다 라이프 풀을 새로 시작하는 것은 '월드 전체에서 공유'를 구체화한 동작이다.

## D10. 추가 라이프 보상
- **Chosen**: 드문 추가 라이프 아이템을 둔다. 라이프가 9개일 때 획득하면 1,000점을 준다.
- **Rationale**: 사용자가 추가 라이프와 상한 초과 시 점수 보상을 선택했다.

## D11. 이어하기 저장
- **Chosen**: 계정당 자동 저장 슬롯 1개. 체크포인트 도달과 스테이지 클리어 때 서버에 자동 저장한다. 저장에는 플레이어 진행 위치, 월드·스테이지, 라이프, 해당 스테이지 점수, 해금 상태가 포함된다. 저장 슬롯이 있는 상태에서 새 게임을 시작하면 덮어쓰기 확인을 받는다.
- **Rationale**: 사용자가 자동 저장 시점, 단일 슬롯, 덮어쓰기 확인을 선택했다. 저장 필드는 선택된 이어하기 동작에 필요한 최소 게임 상태다.

## D12. 점수 및 랭킹
- **Chosen**: 스테이지마다 점수를 0부터 시작한다. 코인 100점, 적 처치 200점, 스테이지 완료 500점. 추가 라이프 획득 시 최대 라이프를 넘으면 1,000점 보너스를 준다. 점수별 동점은 클리어 시간이 짧은 순으로 정렬한다. 랭킹은 스테이지별·누적 방식이며 각 플레이어의 최고 점수 하나만 표시한다.
- **Rationale**: 사용자가 점수 항목, 배점, 스테이지별 초기화, 동점 기준, 플레이어별 최고 기록과 누적 랭킹을 선택했다.

## D13. Entra ID 로그인 및 기록 이름
- **Chosen**: 회사 Entra 테넌트 구성원 모두 로그인 가능. React에서 MSAL로 로그인하고, Azure Functions가 Entra 액세스 토큰을 검증한다. 랭킹에는 Entra 표시 이름만 표시한다.
- **Rationale**: 테넌트 전체 허용, MSAL과 API 토큰 검증, Entra 표시 이름 사용을 선택했다. SPA 인증에는 인증 코드 흐름과 PKCE를 사용한다.

## D14. 랭킹 입력 검증
- **Chosen**: 서버에서 기본 검증을 수행해 스테이지 완료 여부와 점수·시간의 허용 범위를 확인한다. 게임 전체를 서버 권위 방식으로 시뮬레이션하지는 않는다.
- **Rationale**: MVP 범위에 맞춰 기록 위조의 기본적인 방어를 하고, 전체 서버 시뮬레이션은 제외하기로 했다.

## D15. 연결 끊김 동작
- **Chosen**: 연결이 끊기면 게임을 일시 정지하고 자동 재연결을 시도한다.
- **Rationale**: 서버 저장과 랭킹 제출이 필요한 게임 흐름에서 오프라인 진행 중 기록 불일치를 줄인다.

## D16. 구현을 위한 데이터·API 세부사항
- **Chosen**: 플레이어 식별은 Entra 테넌트 ID와 사용자 객체 ID 조합으로 한다. 사용자별 저장 데이터는 하나만 유지하고, 스테이지별 최고 기록은 플레이어·스테이지 조합으로 갱신한다. Functions API는 인증된 요청만 받고, API에서 다시 테넌트와 토큰 대상(audience)을 확인한다.
- **Rationale**: 위에서 선택한 단일 테넌트·단일 저장·플레이어별 스테이지 최고 기록을 안정적으로 구현하기 위한 서버 측 세부사항이다.

## D17. 이후 플레이어블 캐릭터 추가
- **Chosen**: 캐릭터 정의와 애니메이션 에셋을 데이터 기반으로 등록할 수 있게 설계한다. MVP에서는 현재 주인공 한 명만 선택 없이 사용하고, 캐릭터 선택 UI는 만들지 않는다.
- **Rationale**: 사용자가 추후 플레이어블 캐릭터를 추가하고 싶다고 했고, 첫 버전 주인공은 현재 캐릭터로 지정했다.

## D18. Functions와 Azure SQL 연결 방식
- **Chosen**: Azure Functions는 Static Web Apps 관리형 함수가 아니라 별도 Function App(BYO)을 사용하고 시스템 할당 관리 ID로 Azure SQL에 연결한다.
- **Rationale**: Static Web Apps 관리형 함수는 관리 ID를 지원하지 않는다. 별도 Function App은 관리 ID를 사용할 수 있어 SQL 비밀번호를 앱 설정에 저장하지 않는 구성을 만들 수 있다. Microsoft 문서에 따르면 Static Web Apps는 기존 Function App 연결을 지원한다.

## D19. 월드 2 고난도 점프 스테이지
- **Chosen**: 월드 2 스테이지 3(`mine-3`)을 보스 직전의 고난도 수직 점프 도전 스테이지로 구성한다. 플레이어는 발판을 연속으로 올라 상단 골라인에 도달한다. 제한시간은 120초이며, 체크포인트는 없다. 낙하하면 라이프를 잃지 않고 아래에서 다시 시작한다. 타이머는 계속 흐르고 이미 획득한 코인은 유지된다. 시간이 끝나면 실패 화면을 표시하고, 재도전은 스테이지 시작 지점과 120초 타이머로 새로 시작한다.
- **Rationale**: 사용자가 월드 2에서 점프로 상위 골라인에 도달하는 '인내의 숲' 유형의 스테이지를 요청했고, 보스 직전인 스테이지 3 배치를 선택했다. 낙하를 라이프 손실 대신 진행 리셋으로 처리하는 별도 도전 규칙과 120초 제한시간을 선택했다.

## D20. 보스 커맨드 입력 및 그로기
- **Chosen**: 각 보스는 밟기 3회로 처치한다. 보스마다 밟기 경로를 돕는 상단 발판 등 보조 요소를 둔다. 두 번째 밟기 직후 보스가 광폭화해 더 이상 밟을 수 없게 되며 공격 속도와 이동 속도가 각각 15% 증가한다. 광폭화 시작 5초 뒤 보스별 키 종류와 길이가 다른 화면 커맨드를 제시한다. 월드 1 보스 커맨드 입력 제한은 4초, 월드 2는 6초다. 정답 입력 시 3초간 그로기 상태가 되어 밟을 수 있고, 마지막 세 번째 밟기로 처치한다. 오입력이나 시간 초과 시 보스가 즉시 반격하고 다음 기회에 다시 도전한다.
- **Rationale**: 사용자가 두 보스 모두에 서로 다른 커맨드 패턴을 적용하고, 두 번 밟은 후의 광폭화·속도 상승·커맨드 성공 후 그로기·마지막 밟기 처치를 지정했다. 오입력 반격과 3초 그로기 시간은 앞서 선택한 규칙을 유지한다.

## 코드베이스 확인 결과
- 현재 저장소는 Project Memory Starter Kit이다. React 앱, 게임 코드, Azure 설정 또는 데이터 모델은 아직 없다.
- 기존 게임 기능의 중복 구현이나 호환성 제약은 발견되지 않았다. 구현 계획은 신규 앱 구축 기준으로 작성해야 한다.
- 게임 캐릭터 이미지 초안 두 장은 `assets/character/`에 생성되어 있다. PNG 크롭/프레임 정렬은 아직 되어 있지 않다.
- 저장소에 `.git/`도 아직 없다. 첫 구현 작업은 Git 초기화와 React 앱 골격 생성을 포함해야 한다.
- Azure SQL은 관계형 데이터에 적합하다는 이유로 추천 구성을 채택했다. 실제 사내 구독의 리소스·권한·테넌트 ID는 구현 전에 확인해야 할 환경 설정이며, 저장소에서 확인할 수 없다.

## 인터뷰 후 제안할 아이디어 (미확정)
- 첫 실행 튜토리얼, 키보드 재설정과 색각 친화적 UI는 접근성과 학습을 돕는다.
- 보스 공격 예고 표시와 체크포인트 안내는 난이도 체감을 개선할 수 있다.
- 월간 랭킹이나 운영자 대시보드는 현재 선택된 기간 제한 없는 랭킹 MVP 이후에 검토할 수 있다.
